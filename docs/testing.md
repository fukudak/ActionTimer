# テスト

自動テストの方針・構成と、実ブラウザ・実機でしか確認できない手動検証手順をまとめる。

---

## テスト戦略: Node 組み込みランナー + 自前DOMスタブ

**状態:** Accepted

### 決定
Node.js 組み込みの `node:test` を使い、`vm` で隔離したコンテキストに最小限のDOMスタブを与えて
`app.js` を直接読み込む方式でテストする。テスト方針(正常系 / 境界値 / 異常系の3層)の規約
(ファイル分割・テスト名・日本語docstring)は命名規則として踏襲する。

### 背景
テスト方針のテンプレートはpytest形式だが、この環境のPython 3.9にはpytestが未導入で、
アプリ本体はブラウザ前提のVanilla JS([設計](./design.md): 依存なし・配信前に静的ビルドを実行)である。

### 根拠
- `node:test` / `node:assert` はNode本体に同梱で、npm依存ゼロ。「依存なし」方針と整合する
- 偽の Date / setTimeout / setInterval を注入できるため、72時間経過や燃え尽きの瞬間を
  決定的にテストできる(実ブラウザでは不可能)
- `app.js` を書き換えずそのまま読み込むので、テスト用の特別な構造をアプリ側に要求しない

### 却下した代替案

| 代替案 | 却下理由 |
|--------|----------|
| pytest + Playwright | pytest/Playwrightともに未導入で、導入コストと依存が `node:test` より大きい |
| Jest + jsdom | npm依存と `node_modules` が発生し、依存なし方針に反する |
| ブラウザ上のテストページ | 自動実行・CI化ができず、時刻の偽装も困難 |

### 結果
- DOMスタブは実DOMの完全な再現ではない(textContentの子要素クリア、innerHTMLの簡易パースなど必要分のみ)。
  スタブの忠実度に起因する見逃しは、後述の手動検証手順で補完する
- 実ブラウザでしか起きない事象(Service Worker、プライベートモード、A2HS)は
  自動テストの対象外とし、手動検証に分離した
- `vm` の別レルムで生成された配列は `assert.deepStrictEqual` でプロトタイプ不一致になるため、
  長さ・要素単位で検証する

### 見直し条件
- アプリにビルド工程やnpm依存を導入することになったとき(Vitest等を再検討)
- スタブと実DOMの乖離が原因の不具合が2回以上発生したとき(Playwright導入を再検討)

### 構成と実行

```bash
node --test "tests/*.test.mjs"
```

| ファイル | 役割 |
|----------|------|
| `tests/test_normal_core.test.mjs` | 第1層: 正常系(登録・着手→履歴記録・燃え尽き・再点火・永続化) |
| `tests/test_boundary_core.test.mjs` | 第2層: 境界値(残り12時間・燃え尽きの瞬間など) |
| `tests/test_error_core.test.mjs` | 第3層: 異常系(破損データ・保存失敗など) |
| `tests/test_removal_contract.test.mjs` | 撤去対象のUI・関数・Service Workerバージョンの静的契約 |
| `tests/test_regression_core.test.mjs` | 旧仕様撤去後も維持する入力・日時・大量描画・安全性の回帰網 |
| `tests/helpers/dom_stub.mjs` | DOM / localStorage / タイマーの偽物を与える共通スタブ |
| `tests/test_ui_contract.test.mjs` | 明色一行UI、アクセシブルな進行度名、着手履歴・着手率の存在、編集・並び替え等モック専用機能の混入防止 |
| `tests/test_deployment_contract.test.mjs` | isolated build、LPコピー、静的アセット、Wrangler配信ディレクトリ |

### 手動検証手順

配信物の確認は `npm run build` 後に `dist/about.html` が存在し、`cmp about.html dist/about.html` が成功することを確認する。Wranglerは `wrangler.toml` の `./dist` を配信する。

自動テストでは再現できない、実ブラウザ・実機でしか確認できない項目をまとめる。配信前には `npm run build` で静的アセットを `dist/` に生成する。

### 事前準備

```bash
cd /path/to/ActionTimer
python3 -m http.server 8000
# ブラウザで http://localhost:8000 を開く
```

時間経過の検証には、開発者ツールのコンソールで以下のスニペットを使う(`HOURS` を変えて経過時間を作る):

```js
// 経過時間を偽装した項目を注入する(例: 71時間経過 = 残り1時間)
const HOURS = 71;
const key = "kichijitsu-timer-v1";
const data = JSON.parse(localStorage.getItem(key)) ?? { pending: [], unexploded: [], history: [] };
data.pending.push({ id: crypto.randomUUID(), title: `${HOURS}時間経過テスト`,
  createdAt: Date.now() - HOURS * 3600 * 1000 });
localStorage.setItem(key, JSON.stringify(data));
location.reload();
```

検証後の後始末: `localStorage.removeItem("kichijitsu-timer-v1"); location.reload();`

### 正常系検証

| # | 検証項目 | 手順 | 期待結果 |
|---|---------|------|---------|
| 1 | 点火 | テキストを入力して「点火」 | 燃焼中の一行カードが追加され、導火線メーターが満タンで表示される |
| 2 | 再読込後の保持 | 点火後にページを再読込 | 項目が残り、残り時間が経過分だけ減っている |
| 3 | 着手フロー | 期限内のカードで「着手」を押す | 追加入力なしでカードが消え、履歴セクションにタイトル・着手日時・点火からの経過時間が記録される |
| 4 | 燃え尽きた | 期限切れ項目を表示する | 燃え尽きアニメーション後、「燃え尽きた」一覧へ残る |
| 5 | 再点火 | 「燃え尽きた」の「再点火」を押す | 燃焼中へ戻り、操作時刻から新しい72時間が始まる |
| 6 | 燃え尽きた項目の削除 | 「削除」を押し、確認をキャンセル後に再度確定する | キャンセルでは残り、確定時だけ完全に消える |
| 7 | 導火線の燃え方 | スニペットで36時間経過の項目を注入 | 導火線が右端から燃え、タイトルと残り時間は読める |
| 8 | 着手率の表示 | 複数件を着手・燃え尽きさせる | 履歴セクションに平均着手時間と着手率(着手件数/(着手件数+燃え尽きた件数))が表示される |

### 境界値検証

| # | 検証項目 | 手順 | 期待結果 |
|---|---------|------|---------|
| 1 | タイトル最大長 | 100文字を超えて入力し続ける | inputのmaxlengthにより100文字で打ち止め |
| 2 | 残り12時間の警告色 | スニペットで `HOURS = 60.001` を注入 | 残り時間が赤色・太字になる |
| 3 | 残り12時間ちょうど | `HOURS = 60` を注入 | 警告色にならない(境界は含まない) |
| 4 | 燃え尽きの瞬間 | `HOURS = 71.999` を注入し、燃え尽きるまで画面を開いたまま待つ | 「燃え尽きました」表示→燃え落ちるアニメーション→「燃え尽きた」へ一度だけ移る |
| 5 | 起動時に既に期限切れ | `HOURS = 100` を注入 | 初回描画前に「燃え尽きた」へ正規化され、再読込しても残る |
| 6 | 端末時計の巻き戻し | 点火後、OSの時計を1時間戻す | 導火線が満タン側へ戻る(仕様: 対策しない)。クラッシュしないこと |
| 7 | 大量項目 | スニペットをループで100件注入 | 一覧がスクロールでき、毎秒更新でカクつかない |
| 8 | タイムゾーン変更 | 点火後、OSのタイムゾーンを変更して再読込 | 表示時刻はローカル時刻に追従。残り時間は変わらない(エポックミリ秒基準) |
| 9 | 画面幅の境界 | ウィンドウを320px幅まで縮める / 横向きスマホ | レイアウト崩れ・横スクロールが発生しない |

### 異常系検証

| # | 検証項目 | 手順 | 期待結果 |
|---|---------|------|---------|
| 1 | 破損データで起動 | コンソールで `localStorage.setItem("kichijitsu-timer-v1", "{{{")` → 再読込 | 空の初期状態で起動。コンソールに日本語のエラーログ(キー名と対処を含む) |
| 2 | 保存失敗(プライベートモード) | SafariのプライベートウィンドウやStorage容量を絞った状態で点火 | 画面上部に赤いバナー「保存に失敗しました。…」が表示され、操作は継続できる |
| 3 | バナーの自動回復 | #2 の後、通常モードで開き直して点火 | バナーが消え、正常に保存される |
| 4 | オフライン起動(PWA) | 一度開いた後、開発者ツールのNetworkで「Offline」にして再読込 | Service Workerのキャッシュからアプリが開き、操作できる |
| 5 | オフライン+未キャッシュ | Offlineのまま `http://localhost:8000/nai.html` を開く | 日本語の503メッセージ「オフラインのため読み込めません。…」 |
| 6 | SWキャッシュ更新 | `sw.js` の `CACHE_VERSION` を上げて配信→再読込を2回 | 2回目の再読込で新しいアセットが反映される(→ [運用](./operations.md)) |
| 7 | 2タブ同時操作 | 2つのタブで開き、両方から点火 | 後から操作したタブの内容で上書きされる(既知の制限。クラッシュしないこと) |
| 8 | タブ放置で日付跨ぎ | タブを開いたままPCをスリープ→翌日復帰 | 復帰後の描画が実時間に追いつく(残り時間がワープして正しい値になる) |
| 9 | XSS | タイトルに `<img src=x onerror=alert(1)>` を入力して点火 | 文字列のまま表示され、スクリプトは実行されない |
| 10 | ホーム画面追加(iOS) | SafariでA2HS→起動 | スタンドアロンで起動し、ホーム画面アイコンに `apple-touch-icon.png`(180×180)が使われる |


### 対象外と判断した観点

テスト方針の網羅項目のうち、このアプリの構成(ブラウザ内完結・サーバーなし・ファイルI/Oなし・依存なし)により対象外としたもの:

| 観点 | 対象外の理由 |
|------|-------------|
| 一般ファイルシステム異常 | 任意パスへの直接I/Oはない |
| 外部サービス異常(APIキー・429・5xx等) | 外部API呼び出しが存在しない |
| 環境異常(環境変数・依存パッケージ) | 環境変数・依存パッケージを使用しない |
| プロセスの並行・強制終了・ゾンビ化 | プロセスを生成しない。並行性はタブ間競合として異常系#7で検証 |
| 文字コード混在・BOM | 入力はブラウザ経由で常にUTF-16(JS文字列) |
| 無効な日付(2025-13-01等) | 日付は常に `Date.now()` のエポックミリ秒で生成され、文字列の日付入力が存在しない |
| 循環参照 | UIからは作れない。発生時はsaveStateのcatch(保存失敗バナー)で検知される |
